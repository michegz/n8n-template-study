The 78% is the whole story

More than three in four templates make network calls, HTTP requests, API nodes, database writes, email sends, with no retry configured, no error output branch, and no error workflow set on the workflow itself.

When any of those calls hits a timeout, a rate limit, or an expired credential, the execution stops and nothing tells you. No alert, no retry, no fallback. The workflow does not crash loudly. It stops, and the run disappears into the execution log.

This is the mechanism behind every "our automation quietly stopped working weeks ago" story. It is not exotic. It is the default.

To be fair to the authors: published templates are demonstrations. They are written to show a pattern, not to survive production. The problem is that nobody tells the person importing it that the difference exists, and the workflow looks finished. There is no visual difference on the canvas between a node that will retry and one that will not.

The three that surprised me

Pinned data. 158 workflows, and it is the sneakiest one. Pinned data is replayed on manual runs in the editor. Production ignores it and hits the real source. So the workflow passes every test you run by hand, against a fixed fake payload, and behaves differently the first time it fires for real. It does not look like a defect. It looks like a workflow that works.

Connections pointing at nodes that do not exist. 15 workflows, 34 dead references. One published template, "Automated Lead Scraper: Apify to Google Sheets", has a node named Manual Trigger, while its connections are wired from a node named Start that is not in the file. n8n imports it without a word of complaint. Four of its six nodes are dead on arrival. Anyone who imported that template got a workflow that does nothing, and nothing on screen says so.

One template has an API key sitting in its body. A workflow titled "Creating a Secure Webhook" carries what the checker flags as an OpenAI-style key pasted into a parameter value instead of an n8n credential. One in 1,999 is rare and I am not going to inflate it into an epidemic. It is worth naming because a secret in the workflow body travels in every export, backup and screenshot of that workflow, forever.

What I would check on anything you import

1. Add retries to every network node. Three attempts, a couple of seconds apart. This one change addresses the 78%.
2. Set an error workflow, or give fallible nodes an error branch that records the failure somewhere a human looks.
3. Delete pinned data before you trust a test. If it passed with pinned data, it has not been tested.
4. Search the workflow for placeholder strings before activating it.
5. Set the timezone if anything is scheduled, or your 9am job runs on server time and shifts twice a year.
6. Open the canvas and look for islands. A node with no path back to a trigger never runs.
7. Grep the JSON for anything that looks like a key before you import somebody else's workflow, and before you export your own.

Method, and what it cannot see

Stated up front, because a checker that hides its blind spots is worse than no checker.

The checker is static analysis. It reads the exported JSON and matches known failure patterns. It never executed a workflow, and no account access was involved.

What that means it cannot see. It cannot tell you whether your credentials are valid, whether an API you depend on changed its contract, or whether the logic is right. A workflow can pass every one of these checks and still be wrong.

I know that specifically, because it happened to me. I wrote a workflow whose job was to watch other workflows and alert on failures. It passed the checker. Then I rebuilt the test data from scratch instead of reusing my original fixture, and it broke immediately: it was filtering executions on a timestamp field the records did not always carry. In JavaScript a missing date produces an Invalid Date, and every comparison against it is false. Every failure was being filtered out. That workflow would have reported "no failures" forever and looked perfectly healthy doing it.

Static checks find the patterns. Running the thing finds the rest.

Sample bias. These are 1,999 of the 11,518 templates in the public library, taken from the most-surfaced end of it. They are demonstrations by design, and a production workflow inside a company may look nothing like them. What the sample does tell you is what the most-copied starting points on the internet look like, and those are what a great many production workflows were copied from.

One rate is measured, not counted. "78% have no error handling" means 78% of the scanned workflows contain at least one network-facing node with no retry, no error branch, and no error workflow set. A workflow with no network calls at all cannot fail this check, so the figure describes workflows that reach the network, which is nearly all of them.

What this script does not catch. It verifies arithmetic against the stored scan, not the scan itself. If the checker's rules are wrong, every number here is confidently wrong in the same direction. It also does not validate rule names: rename a rule to something invented and the script prints it in the table and still exits 0. And it cannot tell you whether a template changed after it was scanned.

I probed it rather than trust it. Against the published copy, downloaded from this page into an empty directory: dropping one row from findings.jsonl fails with exit 1, duplicating a workflow id fails, inflating one findingCount by 50 fails, and unmodified data passes. Renaming a rule to an invented string is not caught, which is why it is written above. The full probe table is in the header of recount.py.
